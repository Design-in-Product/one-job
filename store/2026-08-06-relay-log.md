## Discretionary review — four gaps found at stand-down

Xian asked me to use my own judgement about what exists only in this
environment. Four things, in descending order of consequence.

### 1. 🔴 The new plan's hard requirement rests on a capability I tested and did not have

The successor brief makes it a **hard requirement** that the successor delegate
all git/mail/log work to code agents and never ask Xian to run git. That's the
right fix for the right problem — my needing his hands for every commit is what
ate the 07-25 memo.

**But a spawned agent inherits the same sandbox as its parent.** Mine had no SSH
key, no `gh`, no credential helper, and no GitHub connector — the registry
returned no GitHub MCP at all. I tested this directly. Delegation failed for me
not because I delegated wrongly but because there was nothing different on the
other end.

Whether kindbook is provisioned differently is **unknown**. Xian has seen other
Cowork agents do exactly this, so it's clearly possible on some configurations —
but nobody has confirmed it for the successor's machine, and the plan already
depends on it.

Added as **§4b of `RELAY-HANDOFF.md`** with a three-command first-boot check to
be run *inside a spawned code agent* (not the parent shell — assuming they match
is the mistake). The failure mode is silent: a successor who quietly falls back
to asking Xian looks like a successor for whom everything is working.

### 2. The keystore checksum existed nowhere

Coral reports the keystore "checksum-verified into durable storage." A grep of
the entire repo found **no checksum recorded anywhere**. So the claim could not
be re-verified by anyone later — a restored file could only be trusted, not
checked.

Computed and published it into `RELAY-HANDOFF.md` §3 before standing down:

```
sha256  8abf3ce172dd2c31332cc59da4a768e95bd9daeb395909674ac2085ac36096cd
bytes   2678
```

This is the house rule applied to the single most losable artifact: a
verification is only a verification if the expected value survives where a
future person can read it.

### 3. A signing key may still sit in a folder named for deletion

A second copy of the keystore was in `~/Developer/one-job-OLD-DELETE-ME/`. I
could not check its current state — that path is outside this session's
connected folders.

The combination is what makes it worth flagging: an Android signing key, in a
directory whose name invites deletion, on a laptop about to be repurposed for a
different project under a different Claude account. It wants a deliberate
removal after the durable copy is checksum-confirmed — not an eventual sweep.

### 4. `RELAY-HANDOFF.md` had gone stale in a way that would mislead

§3 still carried an urgent, unqualified instruction to rescue the keystore —
already done. A successor reading it would either redo the work or distrust the
document. Marked RESOLVED, with the original ask preserved for context rather
than deleted, since the reasoning still explains *why* it mattered.
