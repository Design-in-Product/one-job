## Decision: `project.pbxproj` should NOT be gitignored — the opposite

Xian asked whether to gitignore it, reasonably, since its reverting is what
re-armed the BUNDLEID trap on 07-31.

**No.** `project.pbxproj` *is* the Xcode project — targets, build phases,
settings, file references. Ignoring it would mean a fresh clone has no
buildable iOS project at all. (What *is* conventionally ignored is
`xcuserdata/`, which holds per-user window and scheme state — already covered.)

The actual fix is the inverse: **commit the two lines that keep getting lost**,
so they persist across checkouts and every future tag carries them.

```
DEVELOPMENT_TEAM = YZ4B34YGX9      (was absent → Team came up "None")
CURRENT_PROJECT_VERSION = 2        (was 1)
```

Committing `DEVELOPMENT_TEAM` disarms the trap permanently: a fresh checkout of
any future tag arrives with the paid team already selected, so there is no
moment where the free Personal Team sits one row away in a dropdown waiting to
burn another bundle id.

Note for the record: a Team ID is **not a secret** — it ships inside every
distributed app binary and appears in provisioning profiles. Committing it to a
public repo exposes nothing that isn't already public. (Distinct from the
`.p8` App Store Connect key in `docs/AMBER-XCODE.md`, which *is* a secret and
must stay outside the repo.)

`CURRENT_PROJECT_VERSION = 2` also gets committed so the next cut starts from a
known number rather than from whatever the last checkout happened to leave.

**Checked before theorising** — all three relevant pieces, rc.12 vs main:

|---|---|---|
| `TaskCard.tsx` | fit-to-card type sizing | **byte-identical** |
| `createTask` / `topSortOrder` | new-card placement | **byte-identical** |

So "behind on fixes" could not explain either symptom — the code implementing
both behaviours is the same in rc.12 as in main. That ruled out the obvious
hypothesis and pointed at the build actually running.

**Resolution: the device was still running rc.2.** The TestFlight update had
not been installed. Everything observed was July-3rd behaviour, correctly
absent of features that postdate it. Once updated — Settings showing
**v1.0.0-rc.12**, clipboard-paste backup present — both symptoms were gone.

**Two lessons, both mine:**

1. **The built-current check should have come first.** Coral asks for it in
   every cut memo ("confirm Settings shows v1.0.0-rc.N in the built app"). We
   skipped it before uploading, and I reached for two substantive hypotheses
   (stale WKWebView assets; iOS-only fit-text measurement bugs) before running
   the thirty-second check that settled it. Checking *what is running* precedes
   theorising about *why it behaves oddly* — the same shape as the
   wrong-folder episode on 07-25, where three weeks went to "stuck mount"
   before anyone checked which directory was open.
2. **Testers need the check too.** Xian's own words: "I thought I had updated
   it already tbh but maybe I had not." TestFlight's update state is not
   self-evident. Without the version stamp as a habit, a tester can file a bug
   against a build they are not running — and everyone downstream chases it.
   **Recommend the tester instructions open with "confirm Settings shows the
   expected version."** Cheap, and it protects Dan's feedback from the same
   trap.

Net: no regression, no iOS-specific defect, nothing for Coral to fix. Smoke
test now proceeding against genuine rc.12.

## The push-script failure (08-04) — my worst error of the engagement

`scripts/relay-push.sh`, written on 08-03 specifically to guarantee that
Relay's output actually reaches origin, **silently dropped changes and
reported success while doing it.**

Two compounding defects:

1. It staged only `store/` and `docs/mail/`. I had scoped it that way for
   safety. The consequence: **it could not deliver its own fixes**, because
   `scripts/` was out of scope. A fix to the script sat uncommitted for a day
   while everyone believed it had landed.
2. Its verification asked *"is HEAD an ancestor of origin/main?"* — which is
   **true when nothing was staged at all** and the changes are still sitting in
   the working tree. It measured *sync*, not *delivery*, and printed ✅.

Coral caught it, correctly, from Xian's `git status` paste.

This is the house lesson — indicator vs. observed outcome — committed by the
very tool built to enforce it, which makes it the sharpest instance yet: the
export toast, the type-checker that checked zero files, the stale issue
navigator, and now the delivery-verifier that couldn't observe delivery.

**Compounding it**: I "checked" that script with `bash -n`, which proves only
that it *parses*. I never executed it, never made it encounter a leftover file,
and reported it as verified. For a tool whose entire purpose is catching a
failure mode, "it has valid syntax" was the wrong bar — and presenting it as a
check was the same error one level up.

Fixed in `bafb864`: `scripts/` in scope, extra paths accepted as arguments,
post-commit listing of any tracked file left behind, and ✅ only when the
commit is on origin/main **and** nothing tracked remains. Confirmed
independently on github.com rather than from the script's own report.

**Standing rule taken from this**: when I write something whose job is to catch
a failure, I exercise the failure path before handing it over. Parsing is not
testing.
