# R2.1 Root canvas — deep dive

**Author:** Coral · 2026-07-29 · **Status:** FOR DISCUSSION — this is
the next build step; nothing here is committed until we talk. Written
against the actual code, not the vision docs alone.

## What R2.1 is (one sentence)

The top level stops being *a* deck and becomes *the table*: multiple
named decks side by side (work, life, …), the system rooms
(Done/Archive/Trash) standing among them as places, and a way to move
between neighbors — the app's first spatial altitude.

## The central insight: the model already knows how

Every card's interior is `decks: InteriorDeck[]` — named decks of full
recursive cards. The root today is the *only* place shaped differently:
a bare `Task[]`. **The root canvas is "the interior of no card."** So
the schema change is not an invention, it's removing an exception:

```
v2  { schemaVersion: 2, cards: Task[] }
v3  { schemaVersion: 3, decks: InteriorDeck[] }   // v2's cards become
                                                  // decks[0], name null
```

Same shape at every level, which is what Item 17 ("exactly parallel to
multiple top-level decks") anticipated. Gall-compliant: v3 with one
unnamed deck behaves byte-for-byte like v2.

## Staged build (each stage shippable, app works after each)

### Stage 1 — Schema v3 + migration (invisible)
- `migrate.ts` grows v2→v3; **fixture-corpus tests first** (RED ZONE),
  exactly like the v1→v2 pass: real v2 documents including Xian's
  backup shape, plus the paranoia copy (`.v2backup` before first write,
  mirroring the existing `.v1backup` pattern).
- Store internals switch to `this.decks`; every existing API keeps its
  contract by operating on… **all decks** (findCardById walks all) with
  creation defaulting to deck[0]. `getAllTasks()` returns deck[0] until
  the UI learns better — zero visible change.
- Undo stack, snapshots, housekeeping, backup export all operate on the
  document, so they inherit v3 for free (tests to prove it, not assume).
- **Ship: nothing visible. 104+ tests green.**

### Stage 2 — Decks exist (minimal UI, no canvas yet)
- Store API: `listDecks()`, `createDeck(name)`, `renameDeck`,
  `deleteDeck` (empty-only — a deck holding cards can't be deleted;
  cards must be moved out first, the sealed-card lesson generalized).
- UI: hold-menu gains **"Decks…"** → a sheet listing decks (current
  marked), tap to switch, `+ New deck`. The main view renders the
  *current* deck. Persist current-deck choice per device (a UI
  preference, not deck data — localStorage key, not the document).
- New-card creation lands in the current deck.
- **Ship: real multi-deck use, ugly-but-honest switching.**

### Stage 3 — Cards move between decks
- The move grammar extends, it doesn't fork: **promote from a top-level
  card currently refuses** ("refuses to promote a top-level card" is a
  tested behavior). With N root decks, promote-at-top gains a meaning:
  *move to another deck* — the picker lists the OTHER root decks, same
  flat-sheet UI as MoveIntoPicker (same component, different targets).
- Store: `moveCardToDeck(cardId, deckId)` — top of target (newest-on-top
  rule), sealed rules don't apply (root decks aren't cards and can't be
  "done"… **unless we later want deck-level completion — parked, see
  open questions**).
- **Ship: decks are useful, not just separate.**

### Stage 4 — The pan (the canvas becomes felt)
- Horizontal pan **at the deck altitude**: grab the *background* (or a
  peeking edge), not the card — the card already owns horizontal drag.
  Disambiguation is by target, the same trick that already separates
  card-hold from background-hold for the two menus.
- Neighbor decks peek at the edges (a few px of card-back edge — the
  same felt-pile material). System rooms sit at the far right end of
  the strip: … work · life · │ Done · Archive · Trash — "the afterlife
  is to the right" globally rhymes with swipe-right-completes locally.
- ChainView's rooms stop being a separate view reached through
  "Completed": they're places you pan to. The old route stays as a
  shortcut (menu = shortcut principle, R2.4's first payment).
- **Ship: R2.1 done; R2.2 zoom has a floor to land on.**

## Open questions for Xian (the real design calls)

1. **Deck-level "done"?** Stage 3 parks it: can a root deck itself be
   completed/archived (a finished project), or are root decks eternal
   containers? Eternal is simpler and my lean — a *project* that
   completes is a card with an interior, and we already have that.
2. **Default deck name** when v2 migrates: `null` (unnamed, like
   interior decks) or something warm ("Your deck")? I lean null +
   rename affordance — no invented data in a migration.
3. **How much pan in stage 4 v1?** Full free pan with physics, or
   paged snaps (one deck per screen, dots)? Paged is Gall; free pan is
   the vision. I lean paged-first.
4. **Does the demo/onboarding change?** A new user with one deck should
   never see deck chrome. (My plan assumes: no chrome until deck #2
   exists — the feature reveals itself when created.)
5. **Rooms placement**: right end of the strip (my lean, the rhyme
   above) or a different altitude entirely (they're *system* places —
   R2.2's zoom could put them below rather than beside)? Cheap to move
   later if paged.

## What R2.1 explicitly does NOT include

Zoom (R2.2), the table material design (R2.3), canvas homes for
Settings/Integrations (R2.4), per-deck afterlife (R2.6). Each has a
floor to land on once this ships.

## Risks

- **Migration touches Xian's live deck** — the one real hazard. Fixture
  tests against his actual backup shape before any code; `.v2backup`
  paranoia copy; and the undo stack + dated snapshots as belt and
  braces. Nothing ships until the corpus passes.
- **Gesture collision** (background-pan vs card-drag) — prototype in
  stage 4 with Playwright screenshots before polishing; fall back to
  paged-with-buttons if drag targets fight on real touch.
- **Remote mode (ApiTaskStore)** has no deck concept server-side: it
  presents as a single-deck v3 (deck[0] adapter) until the backend
  learns decks — acceptable, remote is the minority path post-pivot.
- **Beta-week discipline**: stage 1 lands on main only after the R1
  gate reads out, or behind the rc.14 stamp with Relay told — main
  never silently drifts past a memo'd stamp again.
