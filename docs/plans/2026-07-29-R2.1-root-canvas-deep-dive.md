# R2.1 Root canvas — deep dive

**Author:** Coral · 2026-07-29 · **Status:** FOR DISCUSSION — this is
the next build step; nothing here is committed until we talk. Written
against the actual code, not the vision docs alone.

## What R2.1 is (one sentence)

The top level stops being *a* deck and becomes *the table*: multiple
named decks side by side (work, life, …), the system rooms
(Done/Archive/Trash) standing among them as places, and a way to move
between neighbors — the app's first spatial altitude.

## The central insight: the model already knows how

Every card's interior is `decks: InteriorDeck[]` — named decks of full
recursive cards. The root today is the *only* place shaped differently:
a bare `Task[]`. **The root canvas is "the interior of no card."** So
the schema change is not an invention, it's removing an exception:

```
v2  { schemaVersion: 2, cards: Task[] }
v3  { schemaVersion: 3, decks: InteriorDeck[] }   // v2's cards become
                                                  // decks[0], name null
```

Same shape at every level, which is what Item 17 ("exactly parallel to
multiple top-level decks") anticipated. Gall-compliant: v3 with one
unnamed deck behaves byte-for-byte like v2.

## Terms used here (asked 2026-07-29 — a two-line glossary)

- **Room** — one of Done / Archive / Trash: the lifecycle *places* a
  card advances through after the deck (R1.2). Coined in ROADMAP.md
  R1.2 and the ChainView header; the code's `cardRoom()` returns which
  one a card is in. Today the rooms live behind the "Completed" menu
  item; "built to be re-homed as canvas places in R2" was written into
  ChainView on day one.
- **Strip** — MY coinage in this doc, nothing older: the proposed
  stage-4 horizontal row of places you pan along — user decks first,
  system rooms at the right end. If a better word exists, the concept
  doesn't care what we call it.
- Full briefing beyond deltas: **ROADMAP.md** (baseline through R4) and
  **GESTURES.md** (the grammar + its dated decision log) are the two
  documents that carry everything this plan assumes.

### The topology, settled (2026-07-29 exchange)

Xian probed whether the right model is deck-inside-card vs
card-inside-card. Settled: the model is **strictly alternating** —
`table → root deck → card → interior deck → card → …` — decks and
cards never skip a turn: no deck directly in a deck, no card directly
in a card. The alternation is load-bearing: deck = place (name +
order, nothing else — hence uncompletable), card = work (face +
lifecycle); a card can own multiple NAMED decks (Item 17), which
bare card-in-card could not express; and every altitude renders as
"a deck of cards," the uniformity zoom will depend on. Corollary: a
future root-deck demotion must acquire a **carrier card** (auto-made,
wearing the deck's name) — it cannot sit directly inside another deck.

### Strip scope, settled (same exchange)

The strip exists for EVERY user from stage 4: a free single-deck
user's strip is **[your deck] │ Done · Archive · Trash** with a subtle
rightward hint — that hint is how the R2 discoverability gate gets
scored. Pro adds more decks left of the divider; the wall gates
plurality, not the canvas.

## Risks

- **Migration touches Xian's live deck** — the one real hazard. Fixture
  tests against his actual backup shape before any code; `.v2backup`
  paranoia copy; and the undo stack + dated snapshots as belt and
  braces. Nothing ships until the corpus passes.
- **Gesture collision** (background-pan vs card-drag) — prototype in
  stage 4 with Playwright screenshots before polishing; fall back to
  paged-with-buttons if drag targets fight on real touch.
- **Remote mode (ApiTaskStore)** has no deck concept server-side: it
  presents as a single-deck v3 (deck[0] adapter) until the backend
  learns decks — acceptable, remote is the minority path post-pivot.
- **Beta-week discipline**: stage 1 lands on main only after the R1
  gate reads out, or behind the rc.14 stamp with Relay told — main
  never silently drifts past a memo'd stamp again.
