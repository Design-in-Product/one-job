## Session #3: Xian's own testing finds a real bug — and it uncovers a bigger one

**"Multi-deck breaks the export feature? I was trying to back up my web
decks and only a few cards are saved."** Treated as urgent immediately —
flagged the DESTRUCTIVE-ACTION PROTOCOL before anything else (don't
trust the backup, don't take any destructive action based on it, his
live data is presumptively fine, the export is what's suspect).

**Root cause, found by reading the actual code, not guessing:**
`SettingsView.buildBackup()` called `getTaskStore().getAllTasks()` —
but `getAllTasks()` is `LocalTaskStore`'s DISPLAY api, scoped to the
active deck by its own getter (`get tasks() { return
this.activeDeck().cards }`). Every root deck that isn't the one you're
currently looking at was silently omitted from every export path
(share sheet, download, clipboard copy — all three funnel through the
same `buildBackup()`). Checked import too, since a correct export is
useless if restore can't reconstruct it: `importTasks()` flattened
whatever it received into the ACTIVE deck, discarding deck boundaries
even for a hypothetically-correct multi-deck backup. Two bugs, same
root gap: nobody updated the backup/restore path when root decks
shipped (rc.16-18).

**Fix (RED ZONE, test-first per CLAUDE.md — TDD zones, this is exactly
"any code that could break existing task operations"):**
- `buildBackup()` now reads `getDecks()` (all root decks, trash-filtered
  per deck) when the store supports it; single-deck stores (remote/API
  mode) unchanged.
- New v3 backup format `{app, version: 3, decks: [...]}`; v1/v2 flat-
  array backups still import exactly as before (verified with a
  dedicated legacy-backup test).
- `importTasks()` now does a full `loadDocument()` replace — same
  method the normal storage-load path uses — instead of a hand-rolled
  flatten-into-active-deck. Matches the interface's own documented
  contract ("replace all tasks") for the first time.
- `SettingsView.tsx`'s import UI needed a second piece of state
  (`pendingImportDecks`) since `importAsSubdeck` (the non-destructive
  alternative) deliberately still wants a flat card list regardless of
  deck structure — kept that path unchanged, only the full-replace path
  changed.
- 3 new store-level tests (multi-deck export source, full-decks restore
  round-trip surviving a cold start, legacy-backup back-compat).
  167/167 total, tsc clean, build clean. Stamped **rc.32**.

The web PWA had been stuck serving whatever built from commit `7fc089c`

**Root-caused properly, not patched around:** `npm ci` failed only under
npm 10 (CI's Node-22 matrix leg) with `Missing: esbuild@0.28.2 from lock
file` — succeeded fine locally under npm 11 (Node 26, Amber's default,
what I'd been testing with). Two prior "fixes" (regenerate lockfile
with local npm 11; regenerate with a truly fresh install) both still
failed identically in CI. Installed Node 22 via `brew install node@22`
(keg-only — confirmed it doesn't shadow or touch Amber's shared default
`node`) to get the EXACT npm 10.9.8 binary CI uses, and reproduced the
failure locally, byte-identical to the CI log. Real cause: vitest's own
nested `vite` dependency was resolving to the rolldown-based 8.x, where
`esbuild` is an OPTIONAL peer dependency — whether npm decides to
satisfy and lock in an optional peer is exactly where `npm ci` goes
non-deterministic between npm versions.

First fix attempt (override pinning the optional peer's version
directly) "worked" per `npm ci` but was wrong in a worse way: it hoisted
esbuild 0.28.2 to the shared top-level slot, breaking the REAL
production build (`vite@5.4.21` needs `^0.21.3`; 0.28's newer transform
behavior isn't compatible — "Transforming destructuring... is not
supported yet"). Caught only because I ran `npm run build` before
trusting a green `npm ci`, not because anything alerted me. Real fix:
override vitest's nested `vite` to `^7.1.0` instead — pre-rolldown,
where esbuild is a regular non-optional dependency, so there's nothing
left for npm to be inconsistent about. Verified deterministic: `npm ci`
succeeded 4/4 (2× each npm version, fresh `node_modules` every time).
