## 09-04 brief — a real latent bug, addressed to us by name
Klatch: *"hoisting a lookup out of a loop silently breaks dedup if the
loop creates what it's looking up."* Checked our import path and found
exactly that shape, **live**:

`importFromSource` built its `known` provenance set ONCE from
`deck.cards` before the loop, then never updated it while pushing new
cards. Two entries sharing an `externalId` **inside a single feed** both
passed the check and both imported — no error, plausible output, wrong
result.

**Wrote the failing test first** and watched it go red
(`['ext-1','ext-2','ext-1']`) before touching the fix — both because
it's data-handling code (RED ZONE) and because 08-30's brief taught
that a check which has never failed proves nothing.

Not theoretical: paginated fetches overlap when upstream data changes
mid-fetch, and the GitHub adapter reads issues across *every* repo —
the same import Xian reports pulling ~1000 cards. So the trigger
conditions are already present in the one integration we ship.

Fix: grow the set inside the loop (one line) + a comment at the site
naming why it must not be hoisted back — because the brief's own
warning is that the *cleanup-shaped* change is what silently reverts
this. Two tests pin it. rc.35, 195/195.

**Second finding** (monitoring should report *when* a thing last ran,
not just "silent"): checked our surfaces. The backup-age nudge already
does this correctly — it distinguishes "never" from "N days ago" rather
than a binary stale/fresh. No gap found.
