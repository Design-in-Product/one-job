## The copy audit turned into a data-integrity fix

Insight 3 says user-facing copy cannot be sharper than the classifier
beneath it. Audit found most One Job errors interpolate the real
message — fine. One exception: **"Oops! Something went wrong"** was the
title over BOTH an unexpected failure and the app correctly refusing to
read a newer build's data. The second isn't a failure at all, and
mislabelling it is actively dangerous: a user told something went wrong
reinstalls, and reinstalling is exactly what destroyed the deck on
2026-07-05. Split by kind; refusals now read "Your tasks are safe — this
app needs updating," in amber rather than alarm red.

**Chasing that turned up the real find.** `saveTasks` stamped
`schemaVersion: CURRENT` unconditionally. A newer build's document that
still has `decks` passes through `migrateDocument` by design (readable
structure, so read it) — but the first save then DOWNGRADED the stored
version and dropped every top-level key this build didn't recognise.
Sequence: run a newer build, run an older one, and the older one
silently rewrites the document into its own older shape. **That is the
2026-08-04 near-wipe's exact mechanism, alive inside the guard written
to prevent it**, and it breaks covenant 4 in the one place the covenant
exists for.

The store now remembers the version it read and any unrecognised
top-level keys, and writes back `max(CURRENT, stored)` with those keys
untouched. Two tests written first, both seen failing. 238 green.

**The path worth noting:** nobody was looking for a data bug. The lesson
was about error copy, the copy audit asked "what does this bucket
actually contain," and the answer led into the save path. A finding two
hops from where the brief pointed.

**My first test was also wrong**, and usefully: I assumed any
schemaVersion > CURRENT throws. It doesn't — the refusal only fires when
the container is unreadable. Correcting the test to match the real
contract is what exposed the passthrough case that had no protection.
