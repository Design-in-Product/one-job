### [Session #3] m-44 audit — three findings, two with teeth
Audited the build scripts as agreed, then swept the app's success
signals since that's the same genus.

**1. `sync-demo-assets.mjs` had a real silent-success hole.** It printed
"demo.html already up to date" whenever `updated === demo` — which is
true both when the references genuinely matched AND when the regexes
matched *nothing*, making `.replace()` a no-op. In the second case
demo.html keeps pointing at a stale bundle hash and the deployed demo
404s its own JavaScript. Testing it, the mixed case is worse than I
first thought: with only the script tag broken it would *write the file
and report success* while the JS reference stayed stale.
Rewritten so every exit names what it examined: tags must be FOUND in
both files, the rewrite is read back from disk and VERIFIED, and the
referenced bundles must EXIST. Proved both paths — normal build reports
the actual hash transition; a deliberately broken demo.html now exits 1
naming which tag is missing (restored via git checkout, which is a
verified restore since the file was committed and clean).

**2. `make-android-keystore.sh` asserted "it is gitignored" without
looking.** The claim happened to be true (`.gitignore:49 *.keystore`,
checked) — but for a file that is the only way to update the app on
Play, an unverified reassurance is the wrong habit. Now runs
`git check-ignore` and reports what it observed, with a loud warning on
the other branch.

**3. Zapier export toast claims a delivery it cannot observe.** `mode:

### [Session #3] Blocked-completion swipe — fixed, and the proof took three tries
Code fix (9432ff3): `onSwipeRight` may now return `false` to refuse a
swipe. SwipeableCard asks BEFORE animating — the old order set `exitX`
first and called the handler after — and on refusal never sets exitX, so
Framer's dragConstraints spring the card back. CardDeck predicts the
refusal with the same `unfinishedDescendants` predicate the store
enforces (not the parent's async handler: by the time a promise resolved
the card would already be gone). Refused swipes get a lighter haptic
than committed ones.

**The verification is the part worth recording, because I got it wrong
twice before getting it right.**

1. First metric — "did the card fly off-screen?" — was *confounded*. On
   a normal top-level block the app descends into the blocking sub-deck,
   so the card unmounts either way and the measurement can't tell a
   fly-out from a navigation.
2. So I found a case with no navigation: unfinished work as a
   GRANDchild under a COMPLETED child. `unfinishedDescendants` still
   refuses, but Index's `blockingDeck` lookup only scans direct children,
   finds nothing to descend into, and the card stays on the main deck.
3. First A/B on that case showed **no difference** — and the reason was
   my own error: I had reverted only SwipeableCard, while CardDeck still
   returned false and skipped the re-deal. A half-reverted control
   proves nothing. Redid it with both files at `9432ff3^`.

With the honest control, the difference is unmistakable — and it is not
the fly-out at all:

| ~220ms after a REFUSED swipe | before | after |
|---|---|---|
| card element | **unmounted** (x: 120 61 · · ·) | still mounted, settling home (129 83 57 46 41 38 37 36 35) |
| what the user sees | **card back, "Tap to reveal your task"** — torn down and re-dealt | the card, face-up, unchanged |

Frames committed to `docs/screens/2026-07-28-blocked-swipe/`. So the
visible defect was the *re-deal*, not the fly-out: `swipeAndRedeal`
flipped the refused card face-down and dealt it again, which is why it
read as "completed, then undone." The fix skips the re-deal entirely.

Lesson, filed under the same heading as everything else today: a
measurement that can't distinguish the two hypotheses isn't evidence,
and a control that only half-reverts the change is worse than no
control — it produces a confident null result.

### [Session #3] Test hardening — found a real hole, not just thin coverage
Existing coverage is genuinely thorough (88 tests over sorting, lifecycle
chain, snapshots/wipe-protection, promote/move, import, sealed cards), so
rather than pad it I went looking for an invariant enforced in the wrong
place. Found one:

**Item 15 — "a card can't complete while unfinished work is inside" —
was enforced ONLY in `Index.tsx`.** Every other half of the sealed-card
invariant (no move-into, no add-card, no add-deck on a completed card)
already lives in the store, and CLAUDE.md is explicit that task state
logic belongs in the domain rather than frontend state. A UI-only guard
means any other path to `completeTask` can silently bury active work
inside a done card — the exact stranding the invariant exists to prevent,
and the thing that cost a day of Xian's trust on 07-26.

RED ZONE, so tests first. Wrote 5, watched 3 fail for the right reason
("promise resolved instead of rejecting" — the store cheerfully completed
over open work) while the two positive controls passed. Then added
`refuseIfUnfinishedInside` to both `completeTask` and
`completeSubstackTask`.

**The best moment was a test that broke itself.** My deep-case test built
its fixture by completing a middle card that had an unfinished interior —
which the new guard correctly refuses. The arrangement had become
impossible through the API, which is precisely the invariant working: no
NEW strandings can be created. But buried work can still ARRIVE (legacy
decks, imports — Xian's real deck had exactly this shape), so the guard
must still fire on the way out. Rewrote that test to seed the buried
shape straight into storage the way an old deck would. That distinction —
can't be built, can still arrive — is now written into the test.

93/93 green, tsc clean. UI behavior verified unchanged by Playwright:
blocked swipe still shows the info toast and springs back (deep AND
top-level), and — the regression that mattered — an ordinary card still
completes and flies out normally.

### [Session #3] Design options for the two gated items
`docs/DESIGN-OPTIONS-2026-07-28.md`. Wrote these against the covenants
rather than against feature lists, because covenant 2 ("new powers
extend the grammar, they don't add chrome") is the one that bites: in
every other task app, search and undo ARE chrome. The question I kept
asking was "what existing gesture already means this?"

**Rooms search/sift.** Named the real problem plainly: sift is O(n), and
at Xian's 134 cards Done outgrows it fast — sift is a lovely way to
browse and a hopeless way to find. Three options; recommended
**search-as-a-filter-on-the-pile** (typing thins the deck the sift walks,
no results list, so covenant 1 survives untouched) and noted it is the
same design minus the place as the eventual "a search result IS a deck"
version, so nothing gets thrown away when R2.1 lands. Riffle/scrub is a
browse answer, not a find answer — complements, doesn't substitute.

**Found a covenant violation in shipped code** while reading: the sift
hint renders `3 of 27`, a tallied pile, against covenant 7 ("the count
is one or none; depth is felt, never tallied"). Trophy in Done, arguably
exactly the dread the covenant guards against in Trash. Flagged rather
than "fixed" — it's a felt call, and it matters now because the search
design leans on the same signal for its scent.

**Multi-step undo.** The insight worth the whole doc: **the chain
already IS undo** for complete/archive/trash, and it beats a stack —
because state is place, reversal never expires and no history has to be
recorded. So the real scope isn't "add multi-step undo," it's the four
actions that lack a place-based reversal: defer, move/promote, edit,
import. Recommended undo-as-a-place (a "Recent" room), which covers all
of them with one mechanism and **retires the Item 16 quiet-mode
blocker** that's been open since 07-05 precisely because undo lives in a
toast. Snapshot rewind kept as a safety net explicitly NOT labelled undo
— it's whole-deck, so it discards unrelated good work, which makes it a
destructive act in an undo costume and squarely the protocol's business.

Left one question genuinely open rather than deciding it: whether an
action card ("you moved Foo into Bar") is a lovely unification or a
category error in an app where every card so far is a thing to do.
